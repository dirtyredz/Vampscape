# Gotchas — Vampscape

Non-obvious traps. Trap → why → do instead. See [ARCHITECTURE.md](ARCHITECTURE.md) and
[DECISIONS.md](DECISIONS.md) for the reasoning behind several of these.

## Don't latch build-mode state off Harmony activate/deactivate patches
**Why:** the game's `StateMachine.OnDeactivate` is empty — leaving build mode never deactivates the
decorate substate, so an activation-vs-deactivation counter leaks a permanent "still decorating" and
the mod hijacks the camera during normal play. **Do instead:** read the live player state each frame
(`DecorateWatch`, cached per frame). It cannot leak and reports the authoritative mode.

## Don't capture the lens baseline on the frame build mode opens
**Why:** Far Sight restores its lenses as it stands down on that same frame, and Unity gives no
`Update` ordering between the two plugins — you can capture Far Sight's *zoomed* value and treat it
as the default, so normal play comes back wrong. **Do instead:** wait `WarmupFrames` (5) before
capturing; the camera is blending over that window anyway. If normal play returns wider/narrower
than you left it, the warmup is too short.

## Don't assume only the mode's camera is live in build mode
**Why:** the game leaves exactly one of Far/Close/TopDown active, but Far Sight reactivates Close as
it hands build mode over, so Close ends up live alongside the mode's camera — the brain renders the
wrong angle and the zoom drives an off-screen camera (looks dead, especially in Floor mode).
**Do instead:** re-assert the rule (`KeepModeCameraAlone`), but only ever *deactivate*, and only
once the mode's own camera is confirmed live — never switch everything off during a blend.

## Don't latch `ScrollGate.ShouldSwallow()` once per frame
**Why:** Unity gives no `Update` ordering between this plugin and the game's state machines; a
latched flag would be read before it was written on whichever frames the order flips, so the wheel
would leak through or stay swallowed a frame late. **Do instead:** recompute it on every getter
call — everything it reads is already frame-stable and the walk is cheap.

## Don't use `KeyboardShortcut.IsPressed()/IsDown()` for the hold binding
**Why:** those end in a modifier-block check that returns false whenever *any* other key is held —
and the player is very often holding a movement key while lining up a placement, so the binding
would simply never fire. **Do instead:** the hand-rolled `Hotkey.IsHeld` (plain `Input.GetKey` on
the main key + modifiers).

## Don't gate controller zoom without the joystick check
**Why:** on keyboard+mouse, Rewired action 24 is *also* bound to the wheel — read it unconditionally
and every scroll tick counts twice (double zoom step). **Do instead:** only read the axis when
`GetLastActiveController()` is a `Joystick`.

## Don't reference the game's bundled assemblies with `<Private>true</Private>`
**Why:** the game ships its own copies of every referenced assembly; copying them next to the plugin
can shadow the game's and break loading. **Do instead:** all `<Reference>`s use `<Private>false</Private>`
(already set in [src/Vampscape.csproj](../src/Vampscape.csproj)).

## Don't hardcode the version in `Plugin.cs`, and don't hand-edit the synced canonicals
**Why:** the version is single-sourced from `<Version>` in the csproj via `GenerateModBuildInfo`;
`PluginVersion` reads the generated `ModBuildInfo.Version`. `pack.ps1` and `Directory.Build.props`
are workspace-synced canonicals regenerated by `../../tools/sync-mod-files.ps1`. **Do instead:** bump
only the csproj `<Version>` when publishing; edit the canonicals in the workspace, not here.

## `ScrollGate` is the load-time risk
**Why:** it patches a property *getter* (`Input.MouseScrollDelta`) by string name + `MethodType.Getter`.
If Harmony can't resolve it, `PatchAll` throws at load. **Do instead:** after any change near it,
check `BepInEx/LogOutput.log` for the `Vampscape … loaded` line (see [TESTING.md](../TESTING.md)).
